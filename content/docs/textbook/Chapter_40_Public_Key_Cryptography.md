# Chapter 40: Public Key Cryptography and Tool Signing

## 40.1 Agentic Digital Signatures

In a decentralized Swarm, anyone can connect to the Orchestrator's WebSocket. To prevent anonymous attackers from injecting malicious commands, the Orchestrator demands mathematical proof of identity for every critical action. This is achieved through **Agentic Digital Signatures**.

Digital signatures rely on Asymmetric Cryptography (Public/Private key pairs) to provide three assurances:
1.  **Authenticity:** Proves the sender is exactly who they claim to be.
2.  **Integrity:** Proves the JSON prompt hasn't been altered mid-transit.
3.  **Non-Repudiation:** Serves as mathematical, legal proof in the `transcript.jsonl` audit log. A rogue Modder cannot falsely claim "I didn't send that destructive command," because the signature could only have been generated by their unique Private Key.

*(Note: DevCore natively supports the three DSS algorithms for generating signatures: DSA, RSA, and ECDSA).*

## 40.2 Tool Signing

The most critical application of Digital Signatures in the Siraugga Engine is **Tool Signing** (Code Signing). 

When a Tier 5 Admin writes a new Python script or bash utility for the AI to use, they wrap the executable file in a digitally signed envelope using their Private Key. 

If a hacker manages to upload a malicious script to the `/playground/` and tricks the AI into executing it, the Orchestrator will intercept the execution. It will check the script for the Admin's digital signature. Because the hacker does not possess the Admin's Private Key, the script will be unsigned, and the Orchestrator will violently drop the execution, saving the Engine from compromise.

## 40.3 The Modder Execution Workflow

When a Modder issues a highly sensitive command to the Swarm, the Orchestrator forces them to mathematically sign the prompt. The workflow operates as follows:

**Phase 1: The Modder Signs the Prompt**
1.  The Modder writes a prompt (e.g., *"Delete the temporary database"*).
2.  The Modder's local computer generates a SHA-256 hash of the prompt.
3.  The Modder's computer encrypts the hash using the Modder's **Private Key**. This encrypted hash is the Digital Signature. 
4.  The prompt and the Digital Signature are sent across the WebSocket to the Orchestrator.

**Phase 2: The Orchestrator Verifies the Signature**
1.  The Orchestrator receives the prompt and the signature. It looks up the Modder's **Public Key**.
2.  The Orchestrator decrypts the signature using the Modder's Public Key. This reveals the Modder's original hash value.
3.  The Orchestrator independently calculates its own SHA-256 hash of the received prompt.
4.  The Orchestrator compares its calculated hash to the decrypted hash. If they match perfectly, it mathematically proves that the Modder sent the prompt, and the prompt was not altered. The Orchestrator allows the Swarm to execute the command.
