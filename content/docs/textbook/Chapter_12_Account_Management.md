# Chapter 12: Account Management and Privilege Architecture

The central orchestrator of the DevCore ecosystem—acting as the ultimate Identity Provider (IdP)—plays a critical role in the security of the framework. In a Zero-Trust AI environment, determining *who* or *what* is interacting with the system is only the first step. The orchestrator must mathematically guarantee that every user, modder, and autonomous subagent possesses an account type strictly tailored to their operational role. 

This enforcement ensures that entities can only access and modify data on a strict "need-to-know" basis, drastically reducing the blast radius of a compromised agent or a malicious prompt injection.

For example, the central Siraugga Orchestrator issues the following primary account classifications:

*   **User Accounts (Tier 2 Modders & Tier 3 Developers):** Utilized for the day-to-day use of system resources. These accounts are jailed strictly to their assigned game project folders (e.g., `game_demo/`). They are permitted to build logic, write JSON states, and execute sandboxed code, but they are entirely blind to the overarching network.
*   **Service Accounts (AI Subagents & Daemons):** Specialized accounts utilized for automated interaction with the operating system. In DevCore, these are the individual autonomous AI agents. They are highly constrained, non-human accounts granted access to specific toolsets (like `write_to_file` or `run_command`) strictly for the duration of their lifecycle.
*   **Guest Accounts (Tier 1 End Users / Players):** Utilized for temporary, highly restricted users who only need to interact with the final compiled application or in-game NPCs. They have absolutely no write access to the underlying logic.

Proper management of these accounts and permissions is the bedrock of securing sensitive information and maintaining the integrity of the live game state.

## Agentic Account Types and Identity Profiling

A fundamental rule of the Siraugga framework is that organizations must **never share accounts** for privileged users, administrators, or AI applications. The administrator account (Tier 5) must only be used to administer the core system (`TIER_CORE_ENGINE`). If a Tier 5 Super Admin were to recklessly use their root account to test an untrusted, malware-infected AI plugin from a community forum, the entire organization—and every connected game server—would be compromised.

Tier 4 App Admins and Tier 5 Super Admins must be intimately aware of the default group and user accounts that are generated by the underlying operating system or standard LLM wrappers. Because cybercriminals and rogue modders are deeply familiar with default configurations and predictable API endpoints, leaving default guest or admin accounts active is an unacceptable security risk. To harden the infrastructure, administrators must replace all default accounts, enforce cryptographic token validation, and disable any inactive agent profiles immediately.

As the Identity Provider (IdP), the DevCore central server is responsible for authenticating the identity of every connection. When a new Tier 2 Modder joins the project, the orchestrator executes a rigid onboarding sequence:

1.  **Identity Profiling:** Creating a localized, cryptographic identity profile for the user.
2.  **Hardware Registration (FAIM):** Registering the Modder’s physical computer and mobile devices, binding their access tokens strictly to their authorized hardware to prevent session hijacking.
3.  **Lifecycle Management:** Disabling or deactivating any accounts that are no longer needed, and purging organizational data from the user’s sandboxes.

### Spatial and Temporal Access Restrictions
To enforce absolute control over the swarm, administrators utilize temporal and spatial restrictions:
*   **Time-of-Day Restrictions:** Controlling precisely when a Modder or a specific AI swarm can log in (e.g., locking out AI compilation tools during peak player hours to save API bandwidth).
*   **Geofencing (Sandbox Confinement):** In traditional IT, geofencing triggers actions when a user crosses a geographic boundary. In DevCore, Geofencing translates directly to **Sandbox Path Confinement**. If a Tier 3 subagent attempts to execute a tool outside its assigned `cwd` (Current Working Directory), the geofence triggers an immediate `PermissionError` and alerts the Admin.
*   **Geolocation (Hardware Locking):** Identifying a Modder based on their physical network location and hardware signature, ensuring they are not connecting from an unauthorized proxy.
*   **Geotagging (Semantic Watermarking):** Adding an identifier to an artifact based on its origin. In DevCore, every generated line of code or JSON file is "geotagged" with the unique UUID of the specific AI agent that created it, ensuring absolute accountability.

## Securing Privileged Accounts

Cybercriminals heavily target privileged accounts (Tier 4 and Tier 5). Because these are the most powerful accounts in the organization—possessing elevated, unrestricted access to deploy game engines, orchestrate raw Linux operating systems, and modify network devices—they are the holy grail for attackers. 

If a threat actor successfully executes an **Agentic Jailbreak** (overwriting a privileged AI’s System Prompt to steal its root access), they gain absolute control over the logic mainframe. To prevent this, organizations must adopt robust, uncompromising practices for securing privileged accounts:

*   **Identify and Reduce:** Audit the system and minimize the number of Tier 5 Admin accounts. Not everyone needs root access.
*   **Enforce the Principle of Least Privilege:** Users, subagents, and daemons must *only* have access to the specific resources (networks, JSON states, and files) absolutely necessary to perform their assigned function. A `QA` agent should not have the ability to modify the server configuration.
*   **Immediate Revocation:** Revoke access rights and kill active AI subprocesses the instant an employee leaves, a Modder goes rogue, or an agent completes its task.
*   **Eliminate Shared Credentials:** Never allow multiple Tier 4 Admins to share a single API key or SSH login.
*   **Automated Rotation:** Automatically rotate privileged account passwords, API keys, and cryptographic tokens every 30 to 60 days.
*   **Record Privileged Sessions:** Every action taken by a privileged AI agent must be meticulously recorded. DevCore accomplishes this by writing immutable **Transcript Logs** (`transcript.jsonl`), preserving the agent's full chain-of-thought and terminal output for forensic auditing.
*   **The Clean Workspace Protocol (Embedded Passwords):** Administrators must implement strict processes to eliminate embedded passwords in scripts or service accounts. In DevCore, this is enforced via the **Clean Workspace Protocol**: AI agents are strictly forbidden from leaving single-use scratch scripts or `.env` files behind. Configuration files containing secrets must be purely ephemeral and deleted immediately after use.
*   **Generate Anomaly Alerts:** The **Raugus Resolver** must continuously monitor the swarm, generating immediate alerts for unusual behavior (e.g., an agent burning an abnormal amount of tokens or typing with a suspicious terminal rhythm).
*   **Multi-Factor Authentication (MFA):** Enforce multi-factor cryptographic validation for all administrative access.
*   **Implement a Gateway:** Place a rigid gateway (The Zero-Restart Web Portal) between the end-user and the sensitive assets, completely isolating the core network from malware or malicious prompt injections.

Continuously securing and locking down these privileged accounts is critical to the survival of the DevCore framework.

## File Access Control

Permissions are the structural rules configured to limit folder or file access for an individual user or AI agent. Following the principle of **least privilege** and "need-to-know" access, entities must be mathematically restricted to only the resources they require. 

For example, a Tier 2 Modder should never be granted read/write access to the entire root directory simply because it is easier to configure. Doing so creates a catastrophic vulnerability; if the Modder's local environment becomes infected, the cybercriminal instantly gains access to the entire server drive.

In the Siraugga framework, File Access Control is violently enforced through the **Five File Classification Tiers**:

1.  **`TIER_SAFE_WORKSPACE`:** The general premises. Game scripts, NPC JSON data, and local assets. Accessible to Tier 2 Modders and Tier 3 Agents.
2.  **`TIER_CORE_ENGINE`:** The server and orchestration scripts (`App Router Module`, `Task Orchestrator Module`). Highly sensitive. Restricted exclusively to Tier 5 Super Admins.
3.  **`TIER_ADMIN_LOG`:** Daemon logs and transcripts. Read-only access for Admins to monitor the system without altering historical truth.
4.  **`TIER_FORBIDDEN`:** The absolute void. Virtual environments (`venv/`), Git internals, and path-traversal escapes. Hard-blocked for all roles, including Admins, to prevent accidental system destruction.

By routing all read/write requests through strict path resolution modules (`resolve_safe_path()`), the orchestrator guarantees that any attempt to traverse outside an assigned folder boundary results in an immediate, localized lockdown.

### Agentic Tool Whitelists (Permission Levels)
In standard operating systems, file access control is defined by Read, Write, and Execute. In the DevCore ecosystem, these traditional permissions are translated directly into **Agentic Tool Whitelists**. When an AI subagent is spawned, the orchestrator equips it with a highly specific set of tools based on its Role (Archetype). 

The primary permission levels include:

*   **Full Control:** The agent possesses unrestricted access to all tools (`write_to_file`, `replace_file_content`, `run_command`, `manage_task`). Reserved strictly for Tier 5 orchestrator operations, allowing the agent to create, modify, delete, and execute anything within the system.
*   **Modify:** The agent is granted tools like `replace_file_content` to change or delete existing code, but it is explicitly denied `write_to_file`, preventing it from spawning new unauthorized files or scratch scripts.
*   **Read and Execute:** The agent is equipped with `view_file` and restricted access to `run_command`. It can see the contents of the workspace and execute compiled test scripts, but it cannot alter the source code. This is the standard whitelist for **`QA` (Quality Assurance)** subagents.
*   **Write:** The agent can use `write_to_file` and `replace_file_content` to build out the project structure, but may not be allowed to execute the code it writes. This is typical for isolated **`Coding`** subagents that must pass their work to a separate QA agent.
*   **Read-Only:** The agent is only equipped with `view_file`. It can survey the workspace, read the lore, and analyze JSON states, but is physically incapable of altering the game. This is the absolute standard for **`Research`** and **`Tech Matcher`** subagents.

## 3.3.5 The Deny Override & Semantic Inheritance

In the Siraugga framework, the **Explicit Deny** is an absolute, non-negotiable law. If a Tier 5 Super Admin (or the Raugus Resolver) flags a specific directory with an Explicit Deny rule, that rule overrides *all* other permission settings. Even if an AI agent possesses a Tier 5 root token, if the Semantic Mantrap denies access to the `/venv/` directory, the orchestrator will ruthlessly terminate the tool call. Explicit Deny is the ultimate failsafe against catastrophic privilege escalation.

### Workspace Inheritance and Volume Transfers
When navigating the complex structure of the `/playground`, the orchestrator must manage how permissions propagate when AI agents generate massive amounts of new code. The local security policy dictates that after parent folder permissions have been set, any new files or folders generated by an AI inside that parent folder natively inherit its constraints.

However, the movement of data between different Modder workspaces (Volumes) changes how these permissions propagate:
*   **Data moved within the same Sandbox (Volume):** Retains its original agentic tags and permissions.
*   **Data copied within the same Sandbox (Volume):** Inherits the specific permissions of its new parent folder.
*   **Data moved or copied to a DIFFERENT Sandbox:** Instantly stripped of its original tags and aggressively inherits the permissions of the new destination. This ensures that if a Tier 2 Modder copies a script from a highly privileged Core Engine folder (if they somehow had read access), the copied file drops to Tier 2 permissions the moment it enters their personal workspace, preventing them from executing it with elevated privileges.

## Agentic Security Policies & Hallucination Lockouts

In a traditional IT environment, administrators configure Windows Active Directory and Local Security Policies (`secpol.msc`) to enforce password rules and lockouts. In the DevCore ecosystem, Tier 5 Admins configure the **Siraugga Swarm Directory**—the central security policy governed by `Access Control Module` that dictates the behavior of all connected Modders and autonomous subagents.

Through the Zero-Restart Web Portal, Admins enforce three critical agentic policies:

1.  **Cryptographic Token Policy (Password Policy):** Instead of requiring an 8-character password with a capital letter, DevCore enforces mathematically rigorous cryptographic standards. Tier 2 Modders and their spawned AIs must authenticate using asymmetric Ed25519 key pairs. These API keys and session tokens must be automatically rotated by the Orchestrator every 30 to 60 days to prevent token leakage.
2.  **Agentic Lockout Policy (Hallucination Clipping Levels):** In traditional IT, typing a password wrong five times locks the user out for 30 minutes. In DevCore, this translates to the **Hallucination Lockout Policy**. If an AI agent attempts to execute an unauthorized tool or access a forbidden directory five times in a row, the Raugus Resolver assumes the agent is suffering from severe Prompt Injection or a recursive hallucination loop. The orchestrator immediately kills the subprocess and hard-locks the agent’s unique UUID for 30 minutes, protecting the server from Semantic Denial of Service (DoS) attacks.
3.  **Orchestration Audit Policies:** DevCore creates comprehensive, immutable security logs (`transcript.jsonl`) to track specific swarming events, including:
    *   **Agent Spawn/Despawn Events** (Account logon/logoff).
    *   **Semantic Directory Access** (When an agent views or writes to a file).
    *   **Policy Changes** (When a Tier 5 Admin hot-patches the `App Router Module` rules).
    *   **Privilege Use** (Tracking exactly when an agent escalates to a `run_command` execution).

## Federated Swarm Authentication (Authentication Management)

Authentication and authorization issues—such as unencrypted API keys or incorrect JSON permissions—are the leading cause of agentic security breaches. Authentication management in Siraugga aims to ensure secure API connections while providing ease of use for Tier 2 Modders.

*   **Federated Agentic Identity Management (FAIM):** The equivalent of a Single Sign-On (SSO) solution. FAIM allows a Modder to authenticate their physical hardware once, giving them the ability to spawn subagents across multiple allowed game projects without needing a unique API key for every single AI.
*   **Third-Party AI Delegation (OAuth):** When a Modder wishes to connect external plugins—such as an Inworld AI NPC or a custom hugging-face model—they use delegated token standards. This grants the external AI temporary, limited access to the game state without handing over the Modder's master credentials.
*   **The Encrypted State Vault (Password Vault):** Protects and stores all underlying API subscriptions and System Prompts required to run the headless LLMs, requiring only a single master cryptographic key from the Admin to unlock the swarm's memory.
*   **System Prompt Validation (Knowledge-Based Authentication - KBA):** If an AI's behavior becomes erratic, the Orchestrator may challenge the agent with a highly specific contextual question (its Physiological DNA). If the agent fails to answer correctly based on its immutable System Prompt, the Orchestrator knows the agent’s memory has been wiped by an injection attack and instantly terminates it.

## Semantic HMAC (Agentic Message Authentication)

Because DevCore relies heavily on WebSocket (WSS) streaming to pass live JSON state deltas between the game server and the AI swarm, transmitting raw, unencrypted data is a catastrophic vulnerability. 

To solve this, DevCore implements **Hash-Based Message Authentication Code (HMAC)** for its agentic pipelines. Using HMAC, when a Tier 3 subagent generates a JSON action (e.g., "Move NPC to coordinates X,Y"), the agent uses a private key identifier to hash the JSON payload. 

When the central orchestrator receives the JSON packet via the WebSocket, it looks up the subagent's private key and calculates its own HMAC. If the hashes match exactly, the Orchestrator knows two things with absolute mathematical certainty:
1.  **Origin Authentication:** The payload definitely came from the authorized subagent, not a rogue script spoofing a WebSocket connection.
2.  **Data Integrity:** The payload was not maliciously altered or injected with hostile code during transmission.

Just as highly secure VPNs use IPsec and HMAC to authenticate network packets, the DevCore architecture relies on Semantic HMAC to guarantee the integrity of every single thought and action generated by the AI swarm.

## Agentic Authentication Protocols

To secure the massive, interconnected web of Tier 2 Modders, headless LLMs, and physical servers, the DevCore ecosystem relies on robust authentication protocols. In traditional networking, the word "entity" refers to a device or a system. In the Siraugga framework, an **Agentic Entity** refers to any active intelligence—whether it is a human Modder, an automated daemon, or an autonomous AI subagent.

An authentication protocol outlines the exact mathematical handshake required for these entities to connect and share data without unauthorized interception. DevCore translates standard IT protocols directly into Agentic Security measures:

### EAP (Extensible Agentic Protocol)
Used for rapid, lightweight authentication. The subagent client sends a hashed token (often a derivation of its API key) to the authentication server. The central Orchestrator holds the master certificate, meaning the lightweight, headless LLM client does not need to store heavy cryptographic certificates to authenticate.

### Semantic CHAP (Challenge Handshake Authentication Protocol)
A critical defense against **Agentic Drift** and mid-session Prompt Injections. Semantic CHAP validates the identity of running subagents using a one-way hashing function. However, unlike protocols that only authenticate once at login, Semantic CHAP *periodically verifies the identity of the AI during transmission*. If an agent is running a long, 20-minute coding task, the Orchestrator will periodically interrupt the JSON WebSocket stream to "challenge" the agent, ensuring its immutable System Prompt has not been covertly overwritten by a malicious game file. 

### RADIUS (Remote Agentic Dial-In User Service)
When simple, high-speed authentication is needed (for example, a basic in-game NPC chatbot), DevCore utilizes a RADIUS-style protocol. It encrypts the user’s authentication token, but transmits the actual JSON state data (username, accounting, and services) in cleartext to prioritize low latency. Because the data is cleartext, Tier 5 Admins must implement strict timestamping to protect the game engine from **Replay Attacks** (where a cybercriminal intercepts a cleartext JSON command like "Grant 100 gold" and replays it to the server a thousand times).

### TACACS+ (Terminal Access Control Agentic System)
The absolute standard for Tier 5 Super Admins and high-level Orchestrator nodes. TACACS+ uses TCP as its transport protocol and encrypts *all* JSON data—including the WSS payloads, tokens, and accounting variables—between the client and the server. Because Tier 5 Admins must define Agentic Control Lists (ACLs), semantic filters, and rigid sandbox privileges, TACACS+ is the mandatory choice for the `TIER_CORE_ENGINE` where sophisticated, fully encrypted authorization is required.

### Cerberus (The Agentic Ticket System - Kerberos)
Translating the traditional Kerberos protocol, Siraugga utilizes the **Cerberus Ticket System** for highly secure, multi-node swarms. Cerberus eliminates the inherently insecure transmission of passwords across the network entirely. It uses a rigorous two-step process:
1.  **The Ticket-Granting Ticket (TGT):** When an AI subagent is spawned, it does not get raw access to the sandbox. Instead, the central Orchestrator issues the agent a TGT.
2.  **The Service Ticket:** When the AI actually needs to execute a tool (e.g., `run_command` via `wsl.exe`), it presents its TGT to the Cerberus server, requesting a specific "Service Ticket" for that exact action. 

Because Cerberus tickets are mathematically timestamped and set to expire within milliseconds, any attempt by a malicious Modder to intercept and reuse an AI's Service Ticket will result in an immediate rejection by the sandbox.

## Validating Agentic Access Control Models

As established in earlier chapters, authentication simply proves *who* the entity is. **Access Control** determines what that entity is allowed to do. The authentication protocols (TACACS+, Cerberus) directly enforce the two master models of the DevCore universe:

*   **Mandatory Access Control (MAC):** The rigid, operating-system level rules that restrict the actions an AI can perform on a physical object (a file, a TCP port, or a device). MAC is the foundation of the **Five File Classification Tiers**. Every folder in DevCore has a mathematical label (e.g., `TIER_CORE_ENGINE`), and every entity has a clearance level. If a Tier 2 Modder attempts to view `App Router Module`, the MAC system instantly rejects it. The Admin cannot override MAC; the OS enforces it.
*   **Role-Based Access Control (RBAC):** The structural foundation of **Agentic Archetypes**. Permissions are granted based on the specific job function of the AI. A `QA` agent acquires Read-Only and Execute permissions natively through its role, while a `Coding` agent acquires Write permissions. Working in combination with MAC, RBAC allows Tier 5 Admins to safely manage massive swarms of hundreds of autonomous subagents across thousands of unique sandbox permissions.
